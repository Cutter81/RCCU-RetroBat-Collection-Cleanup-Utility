RCCU — RETROBAT COLLECTION CLEANUP UTILITY
==========================================
Full Function & Stage Documentation
-----------------------------------

Version: 4.29  
Platform: Windows PowerShell / Windows 11  
Purpose: Maintenance, cleanup, media reconciliation, XML repair, verification, and controlled promotion of RetroBat game collections.

---

1. What RCCU is
----------------

RCCU (RetroBat Collection Cleanup Utility) is a Windows PowerShell utility designed to maintain large RetroBat collections without blindly deleting files or modifying the live gamelist.xml before the repaired data has been checked.

The utility works around a working copy of the RetroBat XML and uses staged processing so individual operations can be enabled or disabled.

The central safety concept is:

> The real gamelist.xml is not the working XML.

RCCU copies the real XML to:

    gamelist_TEST.xml

Processing is performed against that TEST XML. The original gamelist.xml is only promoted/replaced after Stage 9 completes its verification successfully and the user accepts promotion (unless automatic mode is enabled).

---

2. STAGE OVERVIEW
====================

RCCU currently has nine selectable stages:

  Stage | Name | Main purpose
  1 | File & Folder Permissions | Verify/repair the current Windows user's ownership and Modify access recursively
  2 | Duplicate ROM Review | Find duplicate ROM/source files and let the user decide what to recycle
  3 | Empty / Uniform Image Scan | Find completely uniform/empty images such as all-black, all-white, transparent, or solid-green images
  4 | Black-Bar Image Review | Detect images with large black borders and optionally crop them
  5 | Video Normalization | Re-encode videos into a consistent RetroBat-friendly format
  6 | Stale XML Audit | Find XML game entries whose source game file no longer exists
  7 | Media Audit | Match physical media to actual games and classify recognized, unmatched, and ambiguous media
  8 | XML Repair | Repair the working XML by removing broken references and adding missing game/media references
  9 | Final Verification & Promotion | Verify the repaired XML, create a backup, and optionally promote it to the real gamelist.xml

Stage checkbox behavior
-----------------------

Each stage checks its own checkbox/selection state:

    Stage 1 -> stage 1
    Stage 2 -> stage 2
    Stage 3 -> stage 3
    Stage 4 -> stage 4
    Stage 5 -> stage 5
    Stage 6 -> stage 6
    Stage 7 -> stage 7
    Stage 8 -> stage 8
    Stage 9 -> stage 9

The stage selection is handled by Test-StageSelected and the corresponding stage's execution block.

---

3. STARTING RCCU
====================

RCCU opens with a root-directory selection window.

You can:

- Run against the current directory.
- Browse for a RetroBat root/directory.
- Enable automatic processing.
- Enable automatic recursive processing.

The selected root is expected to contain a RetroBat gamelist.xml and the associated ROM/media directories.

Automatic modes
----------------

AUTOMATIC — YES TO EVERYTHING
-----------------------------

Automatically accepts the decisions RCCU is designed to make automatically, including deletion/recycle reviews and final promotion prompts.

AUTOMATIC RECURSIVE ROOT
------------------------

Processes every directory below the selected root that contains its own gamelist.xml, sequentially, and also enables automatic yes-to-everything behavior.

WARNING: Automatic modes can recycle files, crop images, repair XML, and promote the repaired XML without individual confirmation.

RCCU still uses its recovery/recycle mechanism rather than simply issuing unrestricted permanent file deletion for files it sends through the cleanup process.

4. STAGE 1 — FILE & FOLDER PERMISSIONS
======================================

Function
----------------

    Invoke-FileFolderPermissions

Purpose
----------------

Stage 1 checks the entire selected working directory recursively to make sure the actual Windows user running RCCU has the required ownership and Modify access.

It does not hard-code a username.

The current account is determined dynamically with:

    Get-RccuCurrentUserName

What it checks
----------------

RCCU enumerates files and folders under the selected root and checks whether the current user has sufficient access.

If everything is already correct, the stage finishes without changing permissions.

Repair behavior
----------------

If problems are found, RCCU asks whether ownership and Modify access should be repaired.

Repair uses Windows icacls.exe recursively:

- Sets ownership to the current Windows user.
- Grants Modify access.
- Applies inheritance to the tree.
- Rechecks the complete set of items afterward.

The relevant access grant is equivalent to:

    (OI)(CI)M

Safety gate
----------------

Stage 1 is special because permissions are a prerequisite for the rest of the cleanup.

If Stage 1 is not selected, RCCU does not simply ignore permissions. It performs a prerequisite check.

If the current user does not already have the required access, RCCU stops before Stage 2 and tells the user to run Stage 1.

---

5. STAGE 2 — DUPLICATE ROM REVIEW
=================================

Function
----------------

    Invoke-DuplicateReview

Purpose
----------------

Find duplicate ROM/source files at the working collection level and present them for review.

Duplicate matching
------------------

RCCU normalizes filenames before comparing them. It also understands common RetroBat/ROM naming differences.

.m3u playlists receive special handling:

- A .m3u with a matching real game/source file is ignored by duplicate review.
- An unmatched .m3u remains eligible for normal duplicate grouping.

BIN/CUE handling is also accounted for so a BIN payload does not incorrectly become a second game/source entry when its matching CUE sheet represents the actual game entry.

Files containing Disk/Disc are excluded from the normal duplicate-source grouping logic where appropriate to avoid treating multi-disc collections as ordinary duplicates.

Review interface
----------------

Duplicate groups are shown in a checkbox list.

The newest copy is placed first.

The user can choose:

- DELETE — recycle the selected older files in the current group.
- YES TO ALL — keep the newest copy and recycle the older copies for the current and remaining groups.
- NO TO ALL — keep the current group and all remaining duplicate groups.
- SKIP — keep the current group and continue.
- ESC — acts as Skip.

The newest file cannot actually be deleted by the deletion handler even if someone attempts to select it.

In automatic yes-to-all mode, RCCU keeps the newest copy and recycles the older copies.

---

6. STAGE 3 — EMPTY / UNIFORM IMAGE SCAN
=======================================

Function
----------------

    Invoke-UniformImageReview

Purpose
----------------

Find image files that contain essentially one uniform colour/state throughout the image.

This is intended to catch useless or corrupted artwork such as blank images, solid black images, solid white images, transparent images, or accidental solid-green images.

Current detection threshold
---------------------------

The current uniform threshold is:

    100%

The image must meet the corresponding uniform criterion for the entire analyzed image.

The green detection uses a tolerance value of:

    12

Performance
----------------

Images larger than 500 pixels on their largest dimension are reduced for analysis. This allows large collections to be scanned without performing full-resolution pixel analysis on every image.

Image analysis uses multiple worker processes/runspaces.

What happens to flagged images
------------------------------

RCCU creates a review list rather than immediately deleting every flagged image.

The user can select which flagged images should be recycled.

The Stage 3 log records the threshold and the selected actions.

---

7. STAGE 4 — BLACK-BAR IMAGE REVIEW
===================================

Function
----------------

    Invoke-BlackBarCropReview

Purpose
----------------

Detect images with large black borders/letterboxing and offer a crop operation.

This is separate from Stage 3. Stage 3 looks for completely uniform images; Stage 4 looks for images where a useful picture is surrounded by black border areas.

Detection
----------------

RCCU analyzes dark rows and columns around the image edges and calculates a possible crop rectangle.

The crop detector uses the largest stable detected picture area rather than allowing a later dark area/logo to unnecessarily shrink the crop.

Review behavior
----------------

Flagged images can be reviewed before cropping.

The review supports decisions such as:

- YES — crop this image.
- NO — leave it alone.
- DELETE — recycle it.
- YES TO ALL — apply the crop decision automatically to subsequent qualifying images.
- NO TO ALL — stop applying the crop action to subsequent images.

Automatic yes-to-all mode automatically accepts the configured image operation.

---

8. STAGE 5 — VIDEO NORMALIZATION
================================

Function
----------------

    Invoke-FinalVideoNormalization

Despite the historical function name, the stage is presented to the user as:

    Video Normalization

Purpose
----------------

Normalize video files so RetroBat/EmulationStation has a predictable format to decode.

This stage is intentionally not a video crop/trimming stage.

It does not perform:

- Black-bar trimming.
- Black-frame trimming.
- Crop detection for the output.
- Video content trimming.

Output format
----------------

Processed videos are re-encoded as:

- H.264 video (libx264)
- AAC audio
- yuv420p pixel format
- Constant 30 FPS
- Original video resolution preserved
- Audio at 160 kbps
- Audio sample rate 48 kHz

The source filename and extension are retained so existing RetroBat XML paths do not have to be rewritten merely because the video was normalized.

FFmpeg requirements
-------------------

RCCU looks for ffmpeg.exe and ffprobe.exe in:

1. Windows PATH.
2. The RCCU script directory.
3. An RCCU tools directory.
4. C:\ffmpeg\bin.
5. C:\Program Files\ffmpeg\bin.
6. C:\Program Files (x86)\ffmpeg\bin.

If FFmpeg/FFprobe cannot be found, Stage 5 stops with a clear error rather than pretending the videos were processed.

Parallel processing
-------------------

Multiple FFmpeg jobs are run in parallel.

The number of parallel jobs and FFmpeg threads per job are calculated from the processor count to provide substantially faster processing on large collections.

The stage logs queueing, completion, success, and failures.

9. STAGE 6 — STALE XML AUDIT
============================

Function
----------------

    Invoke-StaleXmlAudit

Purpose
----------------

Find <game> entries in gamelist_TEST.xml whose <path> points to a game/source file that no longer exists.

These are stale XML entries.

Safety behavior
----------------

RCCU refuses to treat an empty TEST XML as a valid cleanup target.

If gamelist_TEST.xml contains zero game entries, the stage performs a safety stop rather than allowing an empty XML to progress toward promotion.

User decision
----------------

When stale entries are found, RCCU can remove the stale game entries from the TEST XML.

The real gamelist.xml remains untouched.

The stage reports:

- Number of entries checked.
- Stale entries found.
- Entries removed.
- Entries retained if the operation is skipped.

---

10. STAGE 7 — MEDIA AUDIT
=========================

Function
----------------

    Invoke-MediaAudit

Purpose
----------------

Reconcile physical media files with actual game/source files and the working XML.

This is one of RCCU's most important matching stages.

Media discovery
----------------

RCCU recognizes media directories through its media-tag mapping, including common RetroBat media types such as images, videos, screenshots, marquees, fanart, manuals, titles, and other configured media categories.

.m3u files are deliberately excluded from the media audit. Playlists belong to the ROM/source side of the collection and should not be reported as abandoned artwork/media.

Files in RCCU_RecycleBin are excluded from normal scans.

Files whose filenames contain the sequence xml are excluded from normal game/media discovery. This prevents files such as XML backups from being mistaken for ROMs or media.

XML protection
----------------

Before matching, RCCU builds a list of every physical file that is already referenced by the working XML.

If an existing physical file is explicitly referenced by XML, it is protected from being classified as abandoned solely because its filename does not match the source-game naming convention.

This is particularly important for manuals/PDFs and custom media.

Matching tiers
----------------

RCCU uses conservative matching rather than immediately using an aggressive fuzzy match.

Tier 1 — Strict
---------------

The media base name is compared directly to the game/source filename.

Tier 2 — Existing normalized match
----------------------------------

Known release/region/filename normalization is applied.

Tier 3 — Punctuation-insensitive match
--------------------------------------

Punctuation is ignored while letters and numbers are retained.

Examples:

    Dr. Mario      = Dr Mario
    Game's Title   = Games Title
    Push-Over      = Push Over

But:

    Game 3         != Game
    Version 2.1    != Version 21
    Game 3         != Game 4

This tier exists specifically to handle harmless punctuation differences without destroying numeric identity.

Tier 4 — XML-title-aware matching
---------------------------------

RCCU can use the clean <name> value from the working XML as an alias for the physical game/source file.

This is particularly useful for TOSEC-style media names containing dates, publishers, dump information, region markers, or other release metadata.

For example, a media file can contain much more filename metadata than the actual RetroBat game name while still being associated with the correct source file.

Ambiguous matches
-----------------

RCCU does not automatically choose between multiple possible games.

If one media file matches multiple games, it is classified as ambiguous and reported for review.

This is deliberate. It prevents an aggressive fuzzy matcher from attaching artwork to the wrong game.

Important: Stage 7 does not immediately recycle unmatched media
---------------------------------------------------------------

Stage 7 classifies media.

Actual abandonment/recycle review is deferred until after XML repair, because XML repair may discover that a media file should be referenced by the repaired XML.

This ordering prevents the earlier problem where valid media could be deleted before XML had a chance to reference it.

---

11. STAGE 8 — XML REPAIR
========================

Function
----------------

    Invoke-XmlRepair

Purpose
----------------

Repair the working gamelist_TEST.xml using the physical game/media collection and the results from Stage 7.

XML safety
----------------

The real XML is not edited directly.

RCCU validates the TEST XML after saving it and compares game-entry counts to make sure the XML did not unexpectedly lose entries during the save operation.

An XML containing zero game entries is rejected.

Broken media references
-----------------------

Stage 8 examines media-related XML elements and removes references to physical files that no longer exist.

Normal game metadata such as:

- path
- name
- desc
- rating
- releasedate
- developer
- publisher
- genre
- players
- playcount
- lastplayed

is not treated as physical media paths during this cleanup.

Missing game entries
--------------------

Stage 8 also performs the complementary operation: if a real game/source exists but is missing from the XML, RCCU can add a corresponding game entry to the working XML.

Media references
----------------

Recognized media that matches a game can be added to the appropriate XML game entry when it is not already referenced.

The physical media is not required to have exactly the same filename as the game when one of RCCU's controlled matching tiers identifies the association.

XML path format
----------------

RCCU resolves RetroBat relative paths such as:

    ./media/images/example.png

relative to the selected RetroBat root rather than the PowerShell process's current working directory.

This prevents incorrect absolute-path assumptions.

XML save validation
-------------------

XML writes are performed through a temporary file first.

The temporary XML is reloaded and validated before it replaces the working TEST XML.

The game-entry count must remain consistent with the source XML being saved.

---

12. POST-XML MEDIA ABANDONMENT REVIEW
=====================================

After Stage 7 Media Audit and Stage 8 XML Repair, RCCU performs a second media check when both stages are enabled and completed.

This is intentionally after XML repair.

A media file must survive both tests before it becomes a final recycle candidate:

1. It must still have no recognized game/source match.
2. It must still not be referenced anywhere in the repaired XML.

This is the safeguard that prevents valid manuals, PDFs, screenshots, videos, or other media from being deleted merely because they were not referenced at the beginning of the run.

---

13. STAGE 9 — FINAL VERIFICATION & PROMOTION
============================================

Functions
----------------

    Invoke-FinalVerification
    Invoke-FinalPromotion

These functions together make up Stage 9.

Verification
----------------

RCCU verifies the working TEST XML for the problems that actually matter to the integrity of the game list.

It checks for:

Missing game/source files
-------------------------

An XML <path> points to a game/source that does not exist.

Missing XML game entries
------------------------

A real game/source file exists but has no corresponding XML game entry.

Duplicate XML paths
-------------------

Multiple XML game entries point to the same normalized source path.

Broken media references
-----------------------

An XML media reference points to a physical file that does not exist.

What does NOT automatically fail verification
---------------------------------------------

Unreferenced media is not itself treated as a final XML verification failure.

That is handled by the Media Audit/XML Repair/abandonment workflow.

This distinction prevents harmless extra media from blocking XML promotion.

Verification audit log
----------------------

The final verification report is written to:

    000-VerificationAudit.txt

The report identifies the problem, where it occurs, and how RCCU detected it.

Promotion
----------------

If verification is clean, RCCU asks whether the TEST XML should become the real XML.

Before promotion, the original XML is moved to a backup name such as:

    gamelist.backup.xml
    gamelist1.backup.xml
    gamelist2.backup.xml
    ...

RCCU then promotes:

    gamelist_TEST.xml

to:

    gamelist.xml

If promotion fails, RCCU attempts to restore the original backup automatically.

If restoration also fails, RCCU reports that manual review is required rather than pretending the operation succeeded.

14. RECYCLE / RECOVERY SYSTEM
=============================

Function
----------------

    Initialize-RecycleStrategy
    Move-FileToRecycleBin

RCCU deliberately handles removable media differently from fixed drives.

Removable/SD cards
------------------

If the working root is on a removable drive, RCCU does not rely on the Windows Recycle Bin.

Instead it uses:

    RCCU_RecycleBin

on the same drive.

Files retain their complete original relative path.

Example:

    Original:
    R:\roms\amigacd32\media\manual\Example.pdf
    
    Recovery:
    R:\RCCU_RecycleBin\roms\amigacd32\media\manual\Example.pdf

This makes the operation recoverable without depending on the Recycle Bin behavior of the removable filesystem.

Fixed drives
----------------

Fixed drives initially use the normal Windows Recycle Bin.

If the first real recycle operation fails, RCCU caches that failure and switches to its own RCCU_RecycleBin for subsequent files instead of repeatedly retrying a broken Windows Recycle Bin operation.

Duplicate recovery names
------------------------

If the same recovery destination already exists, RCCU creates a name such as:

    Example (RCCU 1).pdf
    Example (RCCU 2).pdf

Recovery manifest
-----------------

RCCU writes:

    RCCU_RecycleBin\RCCU_RecycleBin_Log.txt

with original and stored paths.

Performance
----------------

Recovery directories are cached and files are moved using .NET File.Move() where RCCU's own recovery bin is used, avoiding unnecessary PowerShell provider overhead on large cleanup runs.

15. IMPORTANT FILENAME RULES
============================

XML-named files
----------------

Any filename containing the three consecutive characters:

    xml

(case-insensitive) is treated as XML-related and excluded from normal game/media discovery.

Examples include:

    gamelist.xml.bak
    some_xml_backup.txt
    exampleXMLfile.dat

This rule is intentionally broad.

Numbered media suffixes
-----------------------

RCCU supports numbered media naming such as:

    Game-01.jpg
    Game -01.jpg
    Game - 01.jpg
    Game-02.jpg
    Game -02.jpg
    Game - 02.jpg
    Game-011.jpg
    Game - 011-marquee.jpg

These can normalize back toward the underlying game title.

The matching logic is designed so a legitimate game title such as:

    Game 3

is not treated as the same thing as:

    Game

---

16. M3U HANDLING
====================

.m3u files are treated as playlists rather than normal artwork/media.

Rules:

- A matching .m3u is ignored by duplicate ROM review.
- An unmatched .m3u can still participate in duplicate/source review.
- .m3u files are excluded from Stage 7 media discovery.
- .m3u files therefore cannot be reported by Stage 7 as abandoned media.

This prevents playlists from being incorrectly mixed into the artwork/media cleanup process.

---

17. BIN/CUE HANDLING
====================

RCCU understands that a disc image may consist of a CUE sheet plus BIN payload.

When an appropriate matching CUE exists, the BIN is treated as payload rather than an independent game entry.

This helps prevent:

- False duplicate detection.
- False missing XML entries.
- False final-verification failures.

21. XML PRESERVATION PHILOSOPHY
===============================

RCCU intentionally follows this order:

    REAL gamelist.xml
            |
            v
    COPY -> gamelist_TEST.xml
            |
            +--> Stage 6 stale XML cleanup
            |
            +--> Stage 7 media audit
            |
            +--> Stage 8 XML repair
            |
            +--> post-repair media abandonment review
            |
            +--> Stage 9 verification
            |
            v
    backup original gamelist.xml
            |
            v
    promote gamelist_TEST.xml
            |
            v
    new gamelist.xml

The real XML therefore remains the protected source until the final promotion operation.

23. PERFORMANCE DESIGN
======================

RCCU is intended for very large collections, so several operations are deliberately parallelized or cached.

Examples:

- Multi-worker image analysis.
- Parallel video normalization.
- Cached recycle strategy.
- Cached recovery directories.
- Direct .NET file moves for RCCU recovery.
- De-duplicated image/media discovery.
- XML file loading/saving through controlled temporary files.

The goal is to avoid repeatedly invoking expensive PowerShell provider operations when thousands of files are involved.

---

24. SAFETY DESIGN SUMMARY
=========================

RCCU's major safety mechanisms are:

1. Working XML copy — live gamelist.xml is not the working document.
2. XML zero-entry protection — an empty TEST XML cannot progress as a valid library.
3. Temporary XML save validation — XML is validated after writing.
4. Final verification — broken game paths, missing XML entries, duplicate paths, and broken media references are checked before promotion.
5. Original XML backup — promotion creates a backup before replacement.
6. Automatic restoration — promotion failures attempt to restore the original XML.
7. XML-reference protection — physical media already referenced by XML is protected from abandonment classification.
8. Deferred media recycling — unmatched media is not immediately recycled during Stage 7.
9. Ambiguous matching protection — multiple possible game matches are not auto-selected.
10. Removable-drive recovery bin — SD/removable media uses RCCU_RecycleBin rather than relying on Windows Recycle Bin behavior.
11. Recovery path exclusion — RCCU does not recursively process its own recovery bin as collection content.
12. Permission prerequisite — Stage 2 cannot begin if the current user lacks required access and Stage 1 was skipped.

Manual / conservative

Use this when cleaning a collection for the first time or when investigating a questionable collection.

Recommended:

- Stage 1 enabled if permissions need checking.
- Stage 2 enabled.
- Stage 3 enabled if image cleanup is wanted.
- Stage 4 enabled if black-border cleanup is wanted.
- Stage 5 enabled when video normalization is required.
- Stage 6 enabled.
- Stage 7 enabled.
- Stage 8 enabled.
- Stage 9 enabled.

Review reports before allowing large-scale cleanup.

Automatic
----------------

Use only after the collection rules have been tested on a representative directory.

Automatic mode is intended for repeatable maintenance once the user is comfortable with RCCU's matching and cleanup behavior.

Automatic recursive
-------------------

Intended for large RetroBat roots containing many independent gamelist.xml directories.

This mode should be treated as a batch-maintenance mode rather than an exploratory first run.

26. IMPORTANT LIMITATIONS
=========================

RCCU is intentionally conservative in several areas.

Ambiguous media
---------------

If multiple games match the same media key, RCCU does not guess.

Punctuation normalization
-------------------------

The punctuation-insensitive tier ignores punctuation but does not ignore numbers.

XML metadata
------------

The XML-title-aware matching tier is designed to handle common release metadata patterns, but unusual naming schemes may still require manual review.

Video normalization
-------------------

Stage 5 normalizes format; it does not attempt to intelligently crop or trim video content.

Black-bar image detection
-------------------------

Stage 4 is a detection/crop workflow and can still require human review for unusual artwork.

Automatic mode
--------------

Automatic mode removes the human confirmation step. It should therefore be used only after the rules have been validated against the collection.

27. EXAMPLE MEDIA MATCHING
==========================

Suppose the game/source is:

    Dr. Mario (1994).xip

and the media is:

    Dr Mario (1994)(Trash)(PD)[m amition.de].png

RCCU can use its title-aware normalization to identify the actual game title instead of treating all release metadata as part of the title.

Likewise:

    Mr. Nutz - Hoppin' Mad (2016-04-21)(Ocean)_(eu).pdf

can be associated with the corresponding game instead of being reduced to an unusable key such as mr.

The final punctuation fallback can also handle differences such as:

    Game's Title
    Games Title

without making:

    Game 3
    Game

match.

28. TYPICAL COMPLETE RUN
========================

A normal full run looks approximately like this:

    1. Select RetroBat root
    2. Initialize recycle/recovery strategy
    3. Check/repair permissions
    4. Review duplicates
    5. Scan uniform images
    6. Copy gamelist.xml -> gamelist_TEST.xml
    7. Review black-bar images
    8. Normalize videos
    9. Audit stale XML entries
    10. Audit media
    11. Repair XML
    12. Re-check unmatched media against repaired XML
    13. Recycle only media that remains genuinely unmatched/unreferenced
    14. Verify TEST XML
    15. Back up original gamelist.xml
    16. Promote TEST XML to gamelist.xml
    17. Generate normalized game-title list
    18. Finish

Individual stages can be disabled through the stage checkboxes, subject to prerequisite/safety rules.

31. FINAL PHILOSOPHY
====================

RCCU is designed around a simple rule:

> Detect first. Protect known-good data. Repair the working XML. Verify everything. Only then touch the live XML.

It is not intended to be a generic "delete anything that looks unused" script.

The matching system is deliberately layered so exact matches are preferred, controlled normalization is used next, punctuation differences are handled without throwing away numbers, XML titles can resolve release-heavy filenames, and ambiguous matches remain visible instead of being guessed.

For large RetroBat collections, the goal is to make maintenance repeatable while keeping the original XML and recoverable files protected throughout the process.
